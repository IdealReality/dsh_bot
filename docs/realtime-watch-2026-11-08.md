# 实时观看 · 六遍（2026-11-08）

本轮的目标不是"再抽几帧"，而是把**看视频**从"整段解码完再开口"改成"边看边能被叫停"，
同时修掉一遍一遍压出来的真实缺陷。每一条都有可复现的实测数据。

## 一、GPU 能不能当"处理视频的职责"（实测：不能，至少不是现在）

用户上一次问的是"显卡是否可以充当处理视频的职责"。实测这台机器（GTX 1050 2GB）：

| 任务（60s 1080p H.264） | CPU | CUDA |
|---|---|---|
| 解码 + 缩到 32×18 + fps=4（真正的采样路径） | **2.62s** | 3.45s（`-hwaccel cuda` + CPU scale） |
| 解码 + `scale_cuda` + 下载回 CPU | — | 7.46s |
| 纯解码（`-f null -`） | **3.96s** | 6.14s |
| 关键帧粗扫（`-skip_frame nokey`, 1Hz） | 0.32s | — |

结论：**在这个负载上 GPU 全面更慢**。原因是采样只要 32×18、时间分辨率 4Hz，
真正的成本是"解一小段再扔掉"，而 CUDA 路径要为每次使用做上下文与显存↔内存搬运；
GTX 1050 的 NVDEC 单路也没有对 1080p 软解形成数量级优势（4 核软解已经够快）。

更关键的事实：**容器里根本没有 GPU** —— `/dev/nvidia*` 不存在，`nvidia-smi` 不存在，
容器内 `ffmpeg -hwaccels` 只有 vaapi/qsv/drm/opencl/vulkan，`docker inspect` 的
`HostConfig.Devices` 是空数组。要走 GPU 必须先上 nvidia-container-toolkit 并给容器
`--gpus all`。在收益为负的前提下，这一步不该做。

那什么情况值得回头做 GPU：4K/HEVC 素材、或多路并发解码。判据是先量，
不信"GPU 一定更快"。

## 四、顺带修的一处"看起来成功其实没做"

`cohere-bridge` 的"该查没查"重写：模型如果没调工具，旧代码仍用它的空口承诺覆盖原答案，
日志打 `→ 重写：`（后面空白）像成功。现在分三种结果（调了✓/调了✗/**没调工具**），
没有一次成功调用就不覆盖原答案。修复后生产日志出现：

```
[qq] 🌐 该查没查（fact-question）→ 重写：没调工具
```

## 五、仍需知道的两件事

1. **下载现在也能被掐断**（`httpGet({signal})`），但**转写（whisper）不能**：
   插话后它会在后台自己跑完，结果被丢弃。要真中断得把 signal 传进 `asr-core` 的子进程，
   收益不大（它不阻塞回复），先记着。
2. **"实时"仍不是逐帧视频流**：现在是"下载→解码→事件切分→出图"的流水线，
   插话时交付的是**已经解出来的那一段**。要更接近人眼，下一步是把 `readRawStream`
   的 `onFrame` 接上增量事件切分（每 3 秒就能给一段描述），而不是等整片。
